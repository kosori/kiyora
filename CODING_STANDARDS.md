# Coding Standards

Read during **review**, not implementation. Every rule here is a judgement call:
if a guardrail could decide it, it belongs in the linter instead.

Code that `bun check` (Biome via `ultracite`) or `bun check-types` rejects never
reaches review. Do not report it.

Scope: `apps/web` — the only workspace with a stack so far.

## Deliberate deviations from the shared config

`ultracite` defaults to `interface`. This repo overrides
`useConsistentTypeDefinitions` to `type`, and `noExplicitAny` is an error
outside test files. Both are intentional: keep them, and do not report them as
findings. A reversion to `interface`, or a loosened `any` rule, is a finding.

## Functions

- Arrow functions for every hand-written function. A `function` declaration is
  reserved for two cases: a framework that requires a named hoisted export, and
  a server handler a test imports directly.
- `useArrowFunction` only flags function *expressions*, so a `function`
  declaration outside those two cases is a real finding.

## Types

- `interface` only for declaration merging or a generic `extends`. Each one
  carries `// biome-ignore lint/style/useConsistentTypeDefinitions: <reason>`
  with a one-line reason. A suppression without a reason is a finding.
- No `any` outside `**/*.test.ts`. Model the genuinely unknown with `unknown`
  and narrow it at the boundary (`instanceof`, a parse, a type guard) rather
  than reaching for a cast.
- `satisfies` to constrain a literal without widening it. `as` only at a real
  boundary, never to silence a mismatch the types could express.

## Components

- One component per file. A second component may share the file only when it has
  no props of its own, no hooks or state, is not exported, and is used once in
  that file. Failing any one of those, it gets its own file.
- Props are named `Props` for the file's own component, and
  `ComponentNameProps` for every other component. Export a props type only when
  a sibling imports it.
- `children` is never hand-written into a named props type. Use
  `React.PropsWithChildren<Props>`; when children are the only prop, use
  `React.PropsWithChildren`.
- Extending a DOM element is `React.ComponentProps<'form'>`, not a hand-written
  copy of that element's props.
- `export default` only where Next.js requires it (`page`, `layout`, `loading`).
  Bind the component to a name — `Page`, `Layout`, `Loading` — and export at the
  bottom:

  ```tsx
  const Page = () => <main />;

  export default Page;
  ```

  Never `export default function`. Everything else is a named export.
- `'use client'` only when the file needs it. A boundary the file could do
  without is a finding.
- Shared client state uses `createContext<T | undefined>(undefined)` with a
  `useXContext()` that throws outside its provider, in a `context.tsx` beside
  its consumers.

## Route files

`page.tsx` and `layout.tsx` take the Next-generated global prop helpers when they
take props at all, never a hand-written type: `PageProps<'/route'>` and
`LayoutProps<'/route'>`. They need no import, and `LayoutProps` already carries
`children`, so a layout never needs `PropsWithChildren` and never declares
`children` itself. A route component that uses no props takes none —
`noUnusedFunctionParameters` is an error. `params` and `searchParams` are
promises: await them.

A hand-written `Readonly<{ children: React.ReactNode }>` is a finding.

## Vendored shadcn files

`components/ui/**` is generated by the shadcn CLI. It legitimately uses
`function` declarations, a bottom `export { ... }` list, `cn` from the `cn`
package, `cva` variants, and `data-slot` attributes. Review only divergence from
the upstream component; the rules above do not apply there.
