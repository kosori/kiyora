# Agent Guidelines for Kiyora

## Project Overview

Kiyora is a Bun-managed Turborepo containing a TanStack Start web application and shared frontend tooling.

```text
apps/
  web/                  TanStack Start application

packages/
  ui/                   Shared shadcn/Base UI components

tooling/
  tailwind/             Shared Tailwind theme and PostCSS configuration
  typescript/           Shared TypeScript configurations
```

The project currently has no database, API, authentication, or persistence layer. Keep the architecture focused on the frontend until a concrete requirement justifies adding a backend boundary.

## Development Commands

Run commands from the repository root:

- **Install dependencies**: `bun install`
- **Start all development tasks**: `bun run dev`
- **Start only the web app**: `bun run dev:web`
- **Build all packages and applications**: `bun run build`
- **Type check all workspaces**: `bun run typecheck`
- **Check formatting and lint rules**: `bun run check`
- **Apply safe formatting and lint fixes**: `bun run fix`
- **Add a shared UI component**: `bun run ui-add`

The web app also provides:

- `bun --cwd apps/web run generate-routes` — regenerate TanStack Router's route tree
- `bun --cwd apps/web run preview` — preview the production build
- `bun --cwd apps/web run build` — build only the web application

Run the test suite with `bunx turbo run test` (or `bun test <package-path>` for one package). Do not claim tests pass unless you have run them.

## Repository Rules

- Inspect the existing structure and conventions before creating new files or folders.
- Keep changes scoped to the requested feature.
- Prefer the existing workspace packages over introducing duplicate utilities or configuration.
- Do not add a database, API, authentication, server abstraction, or domain layer without a concrete product requirement.
- Do not modify generated files manually.
- Do not modify lockfiles by hand. Use Bun commands when dependency changes are required.
- Do not add secrets, credentials, or real environment values to the repository.
- Do not use destructive Git commands such as `reset --hard`, `clean`, force-push, or deleting branches.
- Do not create documentation that contradicts the package manifests or configuration files.

## Architecture and Dependency Boundaries

### Web application

Application code belongs in `apps/web/src`:

- `routes/` contains TanStack file-based routes and route-specific composition.
- `routes/__root.tsx` owns the document shell, global head metadata, stylesheet loading, and development tooling.
- `router.tsx` owns router creation and router type registration.
- `styles.css` is the application Tailwind entry point.
- `routeTree.gen.ts` is generated by TanStack Router and must be regenerated with the route command instead of edited directly.

Keep product-specific components close to the web app unless they are generic and reusable across applications. Add feature folders only when there is a real product boundary to represent.

### Shared UI package

`packages/ui` contains reusable UI components based on shadcn patterns and Base UI primitives.

- Put reusable components in `packages/ui/src/components/`.
- Put reusable hooks in `packages/ui/src/hooks/`.
- Use the package exports when importing components, for example `@kiyora/ui/button`.
- Use the shared `cn` utility from `@kiyora/ui` for class merging.
- Keep application routes, product data, and app-specific business logic out of this package.
- Preserve the accessibility behavior supplied by the underlying Base UI primitives.

The shadcn configuration is present in `packages/ui/components.json`, but its generation workflow is not yet considered finalized. Inspect the configuration and existing package layout before using `ui-add` or changing how generated components are placed.

### Shared tooling

- `tooling/tailwind/` owns shared Tailwind theme tokens and PostCSS configuration.
- `tooling/typescript/` owns shared TypeScript compiler configuration.
- Applications and packages should extend the shared TypeScript configurations rather than duplicating compiler options.
- Tailwind CSS uses the v4 CSS-first configuration. Prefer semantic theme tokens such as `bg-background`, `text-foreground`, `border-border`, and `ring-ring` over hardcoded colors.

## TypeScript

- Use strict TypeScript and preserve the shared `noUncheckedIndexedAccess` behavior.
- Prefer clear inferred types when the surrounding code makes them obvious.
- Define explicit types for public component props, shared data structures, and non-obvious function boundaries.
- Prefer `unknown` over `any` when a value is genuinely unknown.
- Use type narrowing instead of unsafe casts.
- Do not use `as any`, `@ts-ignore`, or `@ts-nocheck` to bypass errors.
- Use `const` by default and `let` only when reassignment is required.
- Prefer meaningful names and extracted constants over magic numbers.
- Use early returns to keep branching shallow.
- Prefer `for...of` when iteration is required.
- Await promises when their result or completion matters.
- Do not add `try`/`catch` unless the code can recover, translate, or report the error meaningfully.

## React and TanStack Start

- Use function components and hooks according to the Rules of Hooks.
- Keep route definitions in `apps/web/src/routes/` so TanStack Router can discover them.
- Use semantic HTML and accessible labels, names, focus states, and keyboard behavior.
- Prefer the existing UI primitives for dialogs, menus, forms, popovers, and other interactive patterns.
- Do not define components inside other components unless there is a clear reason.
- Colocate code that changes together.
- Use `useEffect` only for synchronizing with an external system, such as browser APIs or event listeners.
- Clean up event listeners, subscriptions, and other resources created by effects.
- Use stable, meaningful keys for rendered collections.
- Keep browser-only behavior out of server-rendered code unless the component or effect provides the required boundary.
- Treat TanStack Router's generated route tree as build output, not application source.

## Styling

- Use Tailwind CSS 4 and the shared theme from `@kiyora/tailwind/theme`.
- Prefer existing semantic design tokens and component variants over new ad hoc colors or spacing values.
- Use the existing `cn` helper when combining conditional or override classes.
- Keep class names readable and let Biome/Ultracite sort classes where configured.
- Use the existing font and theme setup before adding new font or color definitions.
- Preserve responsive behavior and keyboard/focus states when modifying interactive components.

## Formatting and Naming

- Follow Biome and Ultracite configuration rather than introducing local formatting rules.
- Use tabs for JavaScript, TypeScript, and JSX indentation.
- Use single quotes for JavaScript, TypeScript, and JSX strings.
- Organize imports using the repository's configured tooling.
- Use `camelCase` for variables and functions.
- Use `PascalCase` for React components and component types.
- Use kebab-case for component filenames when following the existing component convention.
- Use descriptive names for hooks, constants, and route components.
- Add comments only when they explain why the code exists or document a non-obvious constraint.

## Verification Workflow

After making changes:

1. Run the most focused applicable command while iterating.
2. Run `bun run check` for formatting and lint validation.
3. Run `bun run typecheck` for TypeScript changes.
4. Run `bun run build` for route, Vite, Tailwind, or production-output changes.
5. If verification fails because of an unrelated pre-existing issue, report the exact command and error instead of hiding or broadening the change.

Before changing routes, regenerate the route tree with:

```bash
bun --cwd apps/web run generate-routes
```

Review the generated diff, but do not hand-edit `apps/web/src/routeTree.gen.ts`.

## Change Guidelines

- For a new page, add a file-based route under `apps/web/src/routes/` and let TanStack Router generate the route tree.
- For a reusable visual primitive, add or update a component under `packages/ui/src/components/` and follow the existing Base UI/shadcn composition pattern.
- For app-specific UI, keep the component in `apps/web/src` rather than adding product code to `packages/ui`.
- For shared styling, update the theme in `tooling/tailwind/theme.css` only when the token is genuinely shared.
- For compiler behavior, update `tooling/typescript/` rather than copying settings into individual packages.
- When adding a dependency, determine which workspace owns it and keep dependency direction one-way: shared packages must not import from `apps/web`.
- Avoid broad refactors while implementing a focused feature.
